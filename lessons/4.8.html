4.8 · Skills: Teaching Claude Your Way

Skills: packaged procedures Claude loads exactly when relevant — your templates, checklists and house rules, upgraded from things you paste to things Claude just does.

In one breath: A Skill is a folder of instructions (plus optional files and scripts) that Claude discovers by its description and applies automatically when the task matches — the productised form of every template and procedure you've built since Track 2.

What a Skill actually is

Mechanically, a Skill is a folder whose heart is a SKILL.md file: instructions in plain language, plus a name and description — and the description is the trigger: Claude scans available skills' descriptions and loads the full instructions only when the current task matches. Skills can also carry supporting files (reference docs, examples, templates) and even scripts for programmable steps. Three properties explain everything: Progressive loading: only names/descriptions sit in context by default; the body loads on demand. Your 1.2 physics honoured — you can own fifty skills without renting fifty skills' worth of desk. Portability: the same Skill works across the app, Cowork, Claude Code and the API — write once, applies everywhere your work happens. (This is why the ecosystem treats skills as a big deal: they're the unit of reusable AI procedure.) Composability: multiple skills can fire on one task — your brand-voice skill plus your report-format skill plus your data-honesty skill, stacking like well-behaved colleagues.

Skill vs Project vs memory — the placement decision

Mechanism Its nature Put here when… Memory (4.3) Ambient facts/preferences «I'm in IST; concise answers» — greases wheels Project (4.2) A room: context + shelf Material belongs to ONE ongoing context (a client, a domain) Skill A procedure: how to DO a kind of task «How I write reports / process invoices / review contracts» — applies across rooms, triggered by task type The tell you learned in 4.2 completes here: when a Project's instructions grow procedural («when I give you a transcript, always extract decisions like this…»), that procedure wants to be a Skill — usable in every room, not locked in one. Rule of thumb: context lives in Projects; procedure lives in Skills.

Writing skills that fire (and behave)

The description is a targeting system. Write it like 2.2 taught: specific triggers, not vibes — «Use when the user asks for meeting minutes, summaries of transcripts, or action-item extraction» beats «helps with meetings». Vague descriptions cause both failure modes: never firing, and firing everywhere. The body is your best template, matured: the 3.5 anatomy transfers whole — frozen craft, explicit format contracts, edge-case law, truth rules. Plus examples as supporting files (2.3 by attachment). Build them with Claude: describe the procedure conversationally and have Claude draft the SKILL.md — then test on 3 real cases and iterate (2.7). There's even an official skill-creator skill for exactly this. Version and evals (3.5 + 3.6): skills are assets — date them, and keep the 5-case mini-eval that proves each one still works after edits. Trust note: skills can include executable steps, so treat third-party skills like software — install from sources you trust, read what they do. (Your 8.5 instincts, arriving early.)

Recap

Skills are self-deploying procedure: description as targeting system, body as matured template, examples attached, tested both ways (fires when it should, silent when it shouldn't) — context in Projects, procedure in Skills.
