10.1 · What an Agent Actually Is

What an agent actually is — beneath the hype: a tool-use loop that keeps going toward a goal, deciding its own next step. The mechanism is simple; the judgment is everything.

In one breath: An agent is an LLM in a loop — it takes a goal, chooses a tool, sees the result, decides the next step, and repeats until done — so «agent» is not a smarter model but an ARCHITECTURE, and building good ones is about control, not cleverness.

The agent loop, precisely

An agent is an LLM running this loop: 1. Receive a goal → 2. Decide the next action (which tool, what input) → 3. Execute the tool (9.4) → 4. Observe the result → 5. Is the goal met? If no, go to 2. If yes, respond. The model is the decision-maker; tools are the hands (9.4's division, now looping). Each iteration, the model reasons about progress and picks the next step — it's not following a fixed script, it's NAVIGATING toward a goal. Autonomy = how many loops before a human checks in. One loop with approval each step = supervised (Claude Code's ask-first, 7.4). Many loops unattended = autonomous (a scheduled Cowork task, 5.5). The loop is identical; the AUTONOMY DIAL (5.2's reversibility law) is what varies. You've used agents for six tracks: Cowork (5), Claude Code (7), Research mode (4.6) — all this loop, at different autonomy levels with different tools. «Building an agent» means assembling YOUR version: a goal-shape, a tool set, guardrails, and an oversight level.

Why agents are powerful — and why they're hard

Powerful: they handle OPEN-ENDED, MULTI-STEP tasks where you can't script every step — «research this and write a brief», «debug this failure», «process this backlog handling whatever comes up». The model's judgment fills the gaps a fixed program can't (this is genuinely new — traditional software needs every branch specified). Hard, reason 1 — errors COMPOUND: a wrong step early sends the whole loop astray (a mis-read fact → a wrong search → a wrong conclusion). Autonomy multiplies both capability and mistakes. Hard, reason 2 — cost and loops: each iteration is API calls (tokens, 9.7); a poorly-designed agent can loop expensively or get stuck. Loop limits and cost caps aren't optional. Hard, reason 3 — the security surface is maximal (8.5): an autonomous loop with tools reading untrusted content is the lethal trifecta by construction. Agents are where injection is most dangerous, which is why 8.5 came before this track. The synthesis: a good agent is a WELL-CONSTRAINED loop — enough autonomy to be useful, enough control to be trustworthy. The whole track is that balance.

The reframe: don't reach for autonomy first

Anthropic's own guidance (10.2) is emphatic and worth internalising now: most tasks that feel like they need an «agent» are better served by a simpler, more controlled design. The complexity ladder: a single prompt Autonomy is a cost, not a feature: more autonomy = less predictability, harder debugging, bigger security surface, higher cost. You pay all of that for flexibility you may not need. The discipline: start with the simplest thing that could work; add autonomy only where the task genuinely can't be scripted. The 3.1 chain you can inspect beats the autonomous agent you can't, whenever the chain suffices — which is more often than the hype suggests. This is why the course built chains (3.1), then Cowork's supervised loops (5), then this: you learned the controlled versions first, so you reach for autonomy with judgment, not reflex.

Recap

An agent is the tool-use loop kept running toward a goal — an architecture, not a smarter model; autonomy is a cost (compounding errors, expense, debugging, security), so reach for the simplest sufficient design and reserve the loop for the genuinely unscriptable part.
