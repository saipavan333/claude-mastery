15.5 · Build-Along: The Support Deflection Agent

Build-Along #4 — the Support Deflection Agent: answer customer questions using ONLY the company's own documentation, cite the source, and escalate anything low-confidence or sensitive to a human. Sold on one number every support leader cares about — the deflection rate.

In one breath: The Support Deflection Agent takes an incoming customer question, retrieves the relevant passages from the company's own knowledge base (RAG), answers grounded strictly in those passages with a citation, judges its own confidence, and either drafts a reply for human approval or escalates when unsure or when the topic is sensitive — a high-volume agent sold on its deflection-rate ROI (fewer human-handled tickets) with setup around $2,000–$10,000 plus per-seat or per-resolution pricing.

Step 1-2 — Spec, and understand RAG as the core technique

The five parts: Job — on each customer question, answer it from the company's knowledge base with a citation, or escalate. Trigger — a new ticket, chat, or email. Loop + tools — retrieve relevant docs, answer grounded in them, score confidence, draft-or-escalate, log. Guardrails — answer only from the KB, escalate on low confidence or sensitive topics, human approves customer-facing sends, never promise beyond policy. Delivery + report — drafted replies in the helpdesk for approval, an escalation queue, and a deflection-rate dashboard. RAG (retrieval-augmented generation) is the new idea, and it's simpler than it sounds: instead of hoping the model 'knows' the answer, you first retrieve the handful of documentation passages most relevant to the question, then ask the model to answer using only those passages , quoting/citing them. Retrieval means keeping the KB in a searchable form — a vector/semantic index, or the docs exposed through an MCP server (8.4) — and fetching the top matches per question. This is what makes answers accurate and auditable: the reply is anchored to real, current company text, not the model's training data, which is exactly how you kill hallucination for a support use case (3.4/1.6).

Step 3 — Build the retrieve → answer → judge loop

Build the pipeline in stages and test each on real tickets: Prepare the knowledge base. Gather the help docs, FAQs, and policies; chunk them sensibly; index them for retrieval. Garbage in, garbage out — if the docs are wrong or stale, the agent will be too, so KB hygiene is part of the job (and a reason for the retainer). Retrieve. For each question, pull the top relevant passages. Cheap and fast (Haiku can help route/triage). If retrieval returns nothing relevant, that's an immediate escalate — you can't ground an answer with no source. Answer, grounded. Ask a strong model (Sonnet) to answer using only the retrieved passages, cite which doc it used, and explicitly say 'I don't have that in our docs' when the passages don't cover the question. Structured output (9.5) makes the next step clean: return {answer, citations, confidence, sensitive_topic, needs_human}. Judge & route. If confidence is high, the topic isn't sensitive, and there's a real citation → draft the reply for a human to approve. Otherwise → escalate to a human with the context and the retrieved passages attached, so the human starts at 80%, not zero. Note the model split again: cheap retrieval/triage on high volume, strong model only for the answer — support volume is large, so unit economics matter (12.2).

Step 4 — Guard: grounding, escalation, and the human send gate

This agent's guardrails are its entire safety case, because it speaks to customers: Answer only from the KB. The agent must never use outside knowledge or invent policy; if the docs don't answer it, it says so and escalates. A verification check — do the cited passages actually support this answer? — catches the model 'helpfully' going beyond the source. Escalate on low confidence OR sensitive topic. Hard-list the topics that always go to a human regardless of confidence: refunds and billing disputes, security and account access, legal/compliance, cancellations, anything about a specific charge. On these, 'the agent was pretty sure' is not good enough. Human approves customer-facing sends. Especially at launch, the agent drafts and a support human approves — same gate as the inbox agent (15.2), same reason (it acts toward the outside world on untrusted input, 8.5/10.6). As trust and the deflection stats build, the client may choose to auto-send only the highest-confidence, non-sensitive, well-cited answers — their risk decision, made on real data, not on day one. Never promise beyond policy. No goodwill refunds, no exceptions, no 'I'll escalate this to a manager' it can't guarantee — those create obligations. When in doubt, escalate.

Step 5 — Package it on the deflection rate

This agent has the cleanest ROI story in the track, so lead with the number. The metric: deflection rate — the share of incoming questions the agent safely resolves (drafted-and-approved or auto-answered) without a human writing from scratch. Every point of deflection is measurable labor saved. The demo: run it in shadow mode over a week of the client's real tickets and show 'it would have safely handled 47% of these, with citations, and correctly escalated the rest.' That report closes enterprise deals. Pricing: setup $2,000–$10,000 (KB prep, integration, tuning, escalation rules) plus ongoing per-seat or per-resolution — priced on support-hours saved and faster response times (11.4), which dwarf the API cost. The dashboard IS the retainer: deflection rate, escalation rate, and customer-satisfaction on agent-handled tickets, refreshed monthly, prove value continuously. Watch unit economics at high volume (12.2). Verify current rate ranges on the Current facts page and Track 11.

Recap

The Support Deflection Agent answers customer questions using retrieval (RAG) over the company's own knowledge base — grounding every reply in real, cited documentation instead of the model's guesses — and pairs that with confidence-based escalation: it drafts a reply only when confidence is high, the topic isn't sensitive, and there's a real citation, and otherwise hands off to a human with context attached. Sensitive topics (refunds, security, legal, billing) always escalate regardless of confidence, and customer-facing sends are human-approved until data justifies narrow auto-send. Build retrieve → answer → judge → route with a cheap model for triage and a strong one for answers (volume makes unit economics matter), keep the KB clean, and sell it on a measured deflection rate with setup ($2,000–$10,000) plus per-seat/per-resolution pricing — the dashboard is the renewing proof.
