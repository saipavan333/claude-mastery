8.4 · Build Your First MCP Server

Cross the counter: build a real MCP server for your real workflow — a few dozen lines, one hour, and suddenly you're a supplier in the ecosystem you've been consuming.

In one breath: An MCP server is small: with the official SDK, each tool is a function plus a schema plus a well-written description — build one for a system YOU own, wire it into Claude Code, and the M+N world gains a node with your name on it.

Anatomy of a server (the whole thing)

Using the official Python SDK's high-level interface, a server is: a name, some decorated functions, a run call. Genuinely: server.py — a complete, real MCP server from mcp.server.fastmcp import FastMCP import json, datetime mcp = FastMCP("expense-log") LOG = "expenses.json" def _load(): try: return json.load(open(LOG)) except FileNotFoundError: return [] @mcp.tool() def add_expense(amount: float, category: str, note: str = "") -> str: """Record a new expense. Use when the user mentions spending money or asks to log/track a purchase. Amount in rupees. Category must be one of: food, transport, tools, other. NOT for querying past expenses (use list_expenses).""" items = _load() items.append({"amount": amount, "category": category, "note": note, "date": str(datetime.date.today())}) json.dump(items, open(LOG, "w"), indent=2) return f"Logged: {amount} ({category}). Total entries: {len(items)}" @mcp.tool() def list_expenses(category: str = "") -> str: """List recorded expenses, optionally filtered by category. Use for questions about past spending, totals, or history. Read-only: never modifies the log.""" items = _load() if category: items = [i for i in items if i["category"] == category] total = sum(i["amount"] for i in items) return json.dumps({"count": len(items), "total": total, "items": items[-20:]}) mcp.run() copy Read it with your trained eyes: the docstrings are the tool descriptions — they're PROMPTS (8.1), written with 2.2 discipline (when to use, when NOT, the valid categories = edge-case law); the type hints are the schema (typed inputs the model must fill); the functions are ordinary code. That's the entire anatomy. (SDK details drift — verify the current quickstart at modelcontextprotocol.io — but this shape is the durable idea.)

The craft is the interface, not the plumbing

Descriptions decide behaviour — the model picks tools by reading them (8.1's law, now YOUR responsibility). Every description gets: what it does, when to use it, when NOT to (pointing to the right alternative), and constraints. Your 8.1 practice exercise was literally this job. Design tools like extraction contracts (3.3): typed inputs with constrained values, honest returns (counts! totals! — receipts built into responses), errors that EXPLAIN («category must be one of…») because the model READS errors and self-corrects — a clear error message is a self-healing system. Fewer, sharper tools beat many vague ones: five well-described tools with clean boundaries out-perform fifteen overlapping ones (mis-picks scale with ambiguity — the 4.8 skill-sprawl lesson, supplier edition). Safety is designed in, not bolted on: read tools separated from write tools; destructive operations either absent or unmistakably named with confirmation semantics; secrets via environment (7.8); the least-privilege you DEMANDED as a consumer (8.2), now DELIVERED as a builder.

Build → wire → test → iterate (the loop you already run)

Build with Claude Code (obviously): describe the tools, let it scaffold, review the diffs — the 7.8 loop applies; the server is just another project. Wire: claude mcp add expense-log -- python server.py (local stdio — the server runs as a process when needed). Test like 3.6 taught: known-answer calls (does add→list reconcile?), mis-pick probes (ask something that SHOULDN'T trigger your tools — does it stay quiet?), error-path checks (wrong category → does the error teach?). Calibration isn't just for strangers' servers. Iterate on evidence: mis-picks → sharpen descriptions; wrong parameters → tighten schemas/examples; then version it like the asset it is (3.5's discipline — your server is a template that runs).

Recap

Servers are small; interfaces are the craft — tools chosen deliberately (absent beats guarded), descriptions written prompt-grade, receipts in responses, errors that teach, battery-tested before anything relies on it. You're a supplier now.
