9.6 · Caching & Batches: The 90% Discount

Prompt caching and batch processing: the two features that cut costs by up to 90% — turning ideas that «don't quite pencil out» into profitable products.

In one breath: Prompt caching stores a reused prefix (system prompt, documents, examples) so repeat calls pay 10% of the input price for it (5% on Opus 5.5 and Sonnet 5.5, 2.5% on Fable 5.1); the Batch API processes non-urgent requests asynchronously at 50% off — together they're the economics that decide whether a product makes money.

School-kid picture: Photocopying the same 30-page textbook for every student is expensive; keeping one copy in the class library and letting everyone read it is cheap. Caching keeps the unchanging part ready so you don't pay full price for it every time — but the librarian throws the copy away if nobody reads it for five minutes (or an hour, if you paid for the longer shelf), and only your own school's students can use it. Batching is posting letters by regular mail instead of courier: slower, half the price.

Prompt caching: stop paying for what doesn't change

Recall statelessness (9.2): every call resends the whole context — and you PAY to reprocess it every time. But much of it never changes: your big system prompt, the reference documents, the few-shot examples. Caching stops the repeat-payment: How it works: mark a stable prefix as cacheable. The first call processes and caches it (a small write premium, ~1.25×). Subsequent calls that reuse that exact prefix pay a fraction of the input price for the cached part: 0.1× on most models, 0.05× on Opus 5.5 and Sonnet 5.5, 0.025× on Fable 5.1 . A 5-minute cache costs 1.25× to write (refreshed each time it's read); a 1-hour cache costs 2× to write. The simplest start is one top-level cache_control field (automatic caching); explicit breakpoints on content blocks give finer control. The economics: a 10,000-token system prompt + examples, reused across 1,000 calls: without caching you pay for 10M tokens of prefix; with caching on Sonnet 5.5, about one write (12,500 token-equivalents) plus 999 reads at 5% (≈ 500k) — roughly 0.5M. On a big stable prefix, 90–95% of that cost evaporates. The design rule (and why 3.2's ordering mattered): put STABLE content FIRST (system, documents, examples), VARIABLE content LAST (the user's specific query) — so the cacheable prefix is maximal. This is EXACTLY the docs-top-task-bottom layout (3.2) — you learned the cache-optimal structure before you knew caching existed. Caching pays after ~1 reuse (5-min) or ~2 (1-hour) — so it's for repeated-prefix workloads, which is most products.

A 5-minute write costs an extra 0.25× of the prefix; each read saves 0.95× on Sonnet 5.5 (0.9× on Haiku). So the very first read already pays the premium back. A 1-hour write costs an extra 1×; at 0.95× saved per read you need 2 reads (1 ÷ 0.95 = 1.05). That matches Anthropic's rule of thumb: pays after one read (5-min) or two (1-hour). A day of real traffic. A tutor bot on Sonnet 5.5 resends a 30,000-token textbook with each of 3,000 questions a day. Uncached: 3,000 × 30,000 × $2/MTok = $180/day for the textbook alone. Cached, with traffic gaps that let the 5-minute cache expire 100 times a day: 100 writes × 30,000 × $2.50/MTok = $7.50, plus 2,900 reads × 30,000 × $0.10/MTok = $8.70 — $16.20/day, a 91% cut . Switch to the 1-hour cache and expiries might fall to 15 a day: 15 writes × 30,000 × $4/MTok = $1.80, plus 2,985 × $0.003 = $8.96 — about $10.76/day . The question is never «cache or not» — it's «which TTL matches my traffic gaps». Prove it, don't assume it: read usage.cache_creation_input_tokens and usage.cache_read_input_tokens on every response. Zero reads across repeated calls means something in your prefix changes each time (a timestamp in the system prompt, unsorted JSON, a shuffled tool list) or the prefix is below the model's minimum cacheable length. Caches are also per model: a route that bounces between models pays the write on each. (Source: platform.claude.com/docs/en/about-claude/pricing.)

Batch processing: half price for patience

The deal: submit many requests as a batch, get results back asynchronously (most within an hour, up to 24), pay 50% less on both input and output. Half price, for not needing it THIS second. What it's for: anything not real-time — processing a document backlog (9.3), classifying 50,000 records, generating content in bulk, running evals (3.6), overnight analysis. If a human isn't watching a spinner, batch it. The pattern: real-time user requests → normal API (streaming, instant); bulk/background work → Batch API (async, 50% off). Most products have both, and routing work to the right lane is free money. Scale: huge batches (tens of thousands of requests) in one submission — the infrastructure for turning «process everything» from a cost fear into a line item.

Stacking them into product economics

They compose: a batch job with a cached prefix gets BOTH discounts — 50% off the batch, 90–97.5% off the repeated prefix (the multipliers stack). Priya's 50,000-invoice monthly run, batched with her cached extraction prompt, might cost a fraction of the naive price. Plus model mix (1.3): Haiku for the volume, escalate only where needed — the three levers (right model + caching + batching) together can be the difference between 10× cost and 1× cost on the same workload. Why this IS the business: in AI products, gross margin lives here. A support tool that costs ₹2/conversation at ₹20 revenue is a business; the same tool naively built at ₹15/conversation is a charity. The features are unglamorous; the margin they create is the whole game (9.7 makes it arithmetic). Verify current pricing (multipliers and cache durations evolve — docs are truth) — but the PRINCIPLES (don't repay for stable context; trade latency for discount) are permanent economics.

Recap

Caching stops repaying for the stable prefix (~90% off large reused context, and docs-first ordering makes it cache-optimal); batching trades latency for 50% off bulk work; stacked with model mix, they turn unprofitable ideas into businesses — cost engineering is a durable moat.
