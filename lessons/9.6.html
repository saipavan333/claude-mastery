9.6 · Caching & Batches: The 90% Discount

Prompt caching and batch processing: the two features that cut costs by up to 90% — turning ideas that «don't quite pencil out» into profitable products.

In one breath: Prompt caching stores a reused prefix (system prompt, documents, examples) so repeat calls pay ~10% for it instead of full price; the Batch API processes non-urgent requests asynchronously at 50% off — together they're the economics that decide whether a product makes money.

Prompt caching: stop paying for what doesn't change

Recall statelessness (9.2): every call resends the whole context — and you PAY to reprocess it every time. But much of it never changes: your big system prompt, the reference documents, the few-shot examples. Caching stops the repeat-payment: How it works: mark a stable prefix as cacheable. The first call processes and caches it (a small write premium, ~1.25×). Subsequent calls that reuse that exact prefix pay ~0.1× (10%) for the cached part instead of full price. Cache lives ~5 minutes (refreshed on use) or ~1 hour (higher write cost, longer life). The economics: a 10,000-token system prompt + examples, reused across 1,000 calls: without caching you pay for 10M tokens of prefix; with caching, ~1M-ish. On a big stable prefix, 90% of that cost evaporates. The design rule (and why 3.2's ordering mattered): put STABLE content FIRST (system, documents, examples), VARIABLE content LAST (the user's specific query) — so the cacheable prefix is maximal. This is EXACTLY the docs-top-task-bottom layout (3.2) — you learned the cache-optimal structure before you knew caching existed. Caching pays after ~1 reuse (5-min) or ~2 (1-hour) — so it's for repeated-prefix workloads, which is most products.

Batch processing: half price for patience

The deal: submit many requests as a batch, get results back asynchronously (most within an hour, up to 24), pay 50% less on both input and output. Half price, for not needing it THIS second. What it's for: anything not real-time — processing a document backlog (9.3), classifying 50,000 records, generating content in bulk, running evals (3.6), overnight analysis. If a human isn't watching a spinner, batch it. The pattern: real-time user requests → normal API (streaming, instant); bulk/background work → Batch API (async, 50% off). Most products have both, and routing work to the right lane is free money. Scale: huge batches (tens of thousands of requests) in one submission — the infrastructure for turning «process everything» from a cost fear into a line item.

Stacking them into product economics

They compose: a batch job with a cached prefix gets BOTH discounts — 50% off the batch, 90% off the repeated prefix. Priya's 50,000-invoice monthly run, batched with her cached extraction prompt, might cost a fraction of the naive price. Plus model mix (1.3): Haiku for the volume, escalate only where needed — the three levers (right model + caching + batching) together can be the difference between 10× cost and 1× cost on the same workload. Why this IS the business: in AI products, gross margin lives here. A support tool that costs ₹2/conversation at ₹20 revenue is a business; the same tool naively built at ₹15/conversation is a charity. The features are unglamorous; the margin they create is the whole game (9.7 makes it arithmetic). Verify current pricing (multipliers and cache durations evolve — docs are truth) — but the PRINCIPLES (don't repay for stable context; trade latency for discount) are permanent economics.

Recap

Caching stops repaying for the stable prefix (~90% off large reused context, and docs-first ordering makes it cache-optimal); batching trades latency for 50% off bulk work; stacked with model mix, they turn unprofitable ideas into businesses — cost engineering is a durable moat.
