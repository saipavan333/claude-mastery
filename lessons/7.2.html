7.2 · First Session: Install, Talk, Approve, Ship

Your first full session: launch in the right folder, talk like a briefer, approve like a reviewer, and ship something real — the complete loop, walked slowly once.

In one breath: A Claude Code session is a loop — you brief, it plans, you approve, it acts (edit files, run commands), you review diffs, it iterates — and the first-session rituals (right folder, plan first, read diffs, small steps) become lifetime habits.

Launch: three decisions before the first word

Which folder? The launch directory is the agent's world (7.1). For learning: a copied or fresh project folder. For real work: the project's root. Never: your entire home directory. (Desktop app: pick the folder when creating the session; CLI: cd there, then claude .) Which mode? Sessions have permission modes (full tour in 7.4). Day-one default: the standard ask-before-acting mode — every file edit and command proposed first. It's Manual (5.2) wearing terminal clothes. Version control on? If the folder is a git repository, your safety net is industrial-grade. Not a repo? Ask Claude Code to make it one: «initialise git here and make an initial commit» — your first command, and the best habit in this track. (Don't know git? It's a save-point system for folders — that sentence is enough for now; 7.8 completes it.)

The loop, beat by beat

1. Brief — a Track-2 skeleton aimed at the folder: context (what this project is), task (one outcome), constraints (what not to touch), receipts (how we'll know it worked). 2. Plan — for anything non-trivial, ask for the plan first («plan before acting») or use Plan Mode (7.4). Read it. This is THE checkpoint (5.2's law) — disagreements here cost one message. 3. Approve, watchfully — actions arrive as proposals: a command to run, a file edit shown as a diff (old lines out, new lines in, colour-coded). Read diffs like a reviewer: you don't need to understand every line — you need to check SCOPE (only expected files?), INTENT (does the change match the plan?), and SURPRISES (deletions you didn't expect?). 4. It acts and self-corrects — commands run, output streams back, errors get diagnosed and fixed in the loop (Rekha's signature moment, 7.1). Your job: stay oriented, not omniscient. 5. Verify with receipts — the proof YOU specified: tests passing, counts reconciling, the script's output inspected. Then: 6. Commit — «commit this with a clear message» seals the save-point. Small task, small commit, always shippable.

Talking to it well (the dialect)

Reference files naturally: «look at the config in settings.json», «the CSVs in /data» — it reads what it needs; you don't paste file contents (the container has the files; that's the point). Scope requests to bites: «do X» then «now Y» beats «do X, Y, Z, and also W» — small steps keep diffs reviewable and errors local (3.1's chain law, live). Correct like 2.7 taught: keep/change/because works on code: «the merge logic is right; change the date format to ISO — because downstream tools expect it.» Ask for teaching in-line: «before we continue, explain that error and your fix in plain English» — the free education, claimed (7.1). Interrupt freely: Escape stops a runaway action; you're the editor-in-chief, always.

Recap

Right folder, net first, brief in bites, read every diff (scope/intent/surprises), verify receipts, commit small — the loop is the craft, and the habits from session one compound for years.
