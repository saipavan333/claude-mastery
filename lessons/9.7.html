9.7 · Cost Engineering: Model Mix & Token Budgets

Cost engineering as a discipline: model mix, token budgets, and the unit-economics math that decides whether any AI product makes money — the skill that pays for itself.

In one breath: Cost engineering is deliberate design for margin — routing each task to the cheapest capable model, minimising tokens per interaction, applying caching and batching, and modelling cost-per-user against price — turning «will this make money?» from a hope into a calculation.

The unit-economics equation

Every AI product's viability reduces to this: Profit per user = Revenue per user − Cost per user where Cost per user ≈ (interactions × tokens-per-interaction × effective-price-per-token) Cost engineering is pulling every term DOWN without hurting the product: interactions ↓ — product design: solve the user's need in fewer round-trips (a good first answer beats five clarifying ones). tokens-per-interaction ↓ — prompt design (2.2's brevity is now a cost control), context management (9.2's memory strategy), output bounds (max_tokens). effective-price-per-token ↓ — the big one: model mix (1.3), caching (9.6, ~90% off stable prefix), batching (9.6, 50% off bulk). «Effective» because these can put your real price-per-token far below any single model's list price. Model this BEFORE building (a spreadsheet, 20 minutes) and you know if the idea pencils out — turning «I hope this is profitable» into «at ₹X/user cost and ₹Y price, gross margin is Z%.»

The model-mix architecture

The highest-leverage cost move is refusing to use one model for everything (1.3's law, now architecture): Route by task difficulty: a cheap classifier (Haiku) triages incoming work; simple cases → Haiku answers; complex cases → Sonnet or flagship. Most real workloads are 80% simple / 20% hard — so routing puts 80% of volume on the cheapest model. Cascade: try the cheap model first; escalate ONLY when its answer fails a confidence or quality check (1.3's escalation, automated). Pay premium prices only for the fraction that needs them. Right-size per stage (3.1's chains): in a pipeline, each step gets its own model — Haiku extracts, Sonnet analyses, flagship writes the one high-stakes artifact. Never pay flagship prices for extraction. The savings compound: model mix (5–12× on the routed portion) × caching (up to 90% on stable prefix) × batching (50% on bulk) can stack to an order-of-magnitude total cost difference on the same workload at the same quality.

Cost engineering as a sellable service

The pitch that closes itself: «Your AI feature costs ₹X/user; I'll cut it 60–80% without touching quality — via model mix, caching, batching, and prompt optimisation — for a fee that's a fraction of the annual saving.» Pure found money for the client; easy yes. The audit deliverable: instrument their AI calls (what model, how many tokens, cached?), find the waste (flagship-for-everything, no caching, real-time bulk, bloated prompts), model the optimised architecture, quantify the saving. This IS a consulting engagement (11.2, dev tier) and a genuinely scarce skill. Guardrails you install (1.5, now product-grade): spending limits, per-user rate caps, cost monitoring/alerts, a kill-switch — so a bug or abuse can't produce a surprise bill. Companies pay for peace of mind here alone. The honest caveat: optimise for the RIGHT metric — sometimes the flagship's better answer drives more revenue than its extra cost, so «cheapest» ≠ «most profitable». Cost engineering serves margin, not miserliness; the goal is profit-per-user, not minimum-cost-per-user.

Recap

Cost engineering is deliberate design for margin — route by difficulty (model mix), minimise tokens and interactions, stack caching and batching, and model cost-per-user vs price before building; it's a scarce, self-funding, sellable discipline because most builders skip it.
