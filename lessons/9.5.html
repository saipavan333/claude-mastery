9.5 · Structured Outputs: JSON You Can Trust

Structured outputs: the guarantee that Claude's response arrives as valid, schema-conforming JSON — turning «usually parseable» into «always parseable», which is the difference between a demo and a product.

In one breath: Structured outputs force Claude's response to match a JSON schema you define — guaranteed valid, guaranteed shaped — so your code can trust it without defensive parsing; but the schema guarantees form, never truth, so your contracts (null-honesty, totality) still matter.

The problem, then the guarantee

In chat, you asked for JSON with format instructions (2.4) and usually got it — «usually» being the operative, product-killing word. At scale, «usually valid» means «regularly broken»: one malformed response in a batch of 10,000 is a crashed pipeline or a corrupted record. Structured outputs make schema-conformance a GUARANTEE, not a hope: structured.py — a guaranteed shape response = client.messages.create( model="claude-sonnet-5", max_tokens=500, messages=[{"role": "user", "content": invoice_text}], output_config={"format": { # force the shape "type": "json_schema", "schema": { "type": "object", "properties": { "vendor": {"type": "string"}, "amount": {"type": "number"}, "date": {"type": "string"}, "status": {"type": "string", "enum": ["ok", "unreadable"]}, }, "required": ["vendor", "amount", "status"], }, }}, ) # The response is GUARANTEED to match this schema. No defensive parsing. copy Now your code can do data = json.loads(response...) and TRUST it — right keys, right types, valid enum values, every time. The «Here's your data:» preamble can't happen; the invented field can't happen; the type drift can't happen. (Exact API shape evolves — verify current syntax in docs — but the guarantee is the durable idea.)

What it guarantees — and what it emphatically does not

Guarantees (form): valid JSON, correct structure, correct types, enum constraints honoured, required fields present. Syntax risk → zero. This is real and load-bearing. Does NOT guarantee (truth): a schema-valid response can still contain a GUESSED amount, a wrong vendor, a hallucinated value. { amount : 5000} is perfectly valid JSON and perfectly wrong if the model invented 5000. Structure is not correctness. So your contracts still rule (3.3, 9.3): null-honesty («unreadable → null, never guess») must still be in your PROMPT — the schema allows null; your instructions demand it be used honestly. Totality (one output per input) is your pipeline's job. Sampling and reconciliation (5.3) still catch the truth-errors structure can't. Structured outputs remove the syntax-error class entirely, leaving you to focus fully on the truth-error class — which was always the harder, more important one.

Why this makes products possible

Composability: guaranteed-shape outputs snap into pipelines (3.1's chains, coded) — step 2 can rely on step 1's structure, no defensive glue between stages. This is what makes multi-step AI systems maintainable. Database-safety: outputs that go straight into typed database columns need guaranteed types — structured outputs are what let AI write to real schemas without corruption. The relationship to tool use (9.4): tool INPUT schemas already guarantee valid tool calls (strict mode) — structured OUTPUTS extend the same guarantee to Claude's final answer. Both are «the model must produce this shape», enforced at the decoding level. The mental shift: stop writing defensive parsing code that handles Claude's «creativity»; start declaring the shape you need and building on the guarantee. Less code, fewer bugs, real products.

Recap

Structured outputs guarantee Claude's response matches your JSON schema — killing the syntax-error class and freeing you to focus entirely on truth-errors, which your prompt contracts and sampling still guard; structure is form, never correctness.
