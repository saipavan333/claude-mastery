9.2 · Messages: Conversations, Systems, Streaming

The Messages API in full: conversations as data, the system parameter, streaming, and the dials (max_tokens, effort, thinking, stop sequences) that shape every response — plus the two old dials that now return errors.

Start here

The API doesn't remember past calls. To hold a conversation, your code sends the whole chat every time, as a list of messages marked «user» or «assistant». Standing instructions go in a separate system field. Streaming lets the answer arrive word by word, so users aren't left waiting. A few settings tune the call, like max_tokens and effort . Older settings, temperature and prefilling the reply, are rejected by current models.

In one breath: Messages are a list of role-tagged turns you resend each call; the system parameter carries standing instructions; streaming delivers tokens live; and a handful of parameters (max_tokens, effort, thinking, stop_sequences) tune behaviour — temperature and assistant prefill, the classic dials, are rejected by current models.

Everyday picture: Claude has no memory between calls, like a goldfish. Each time, you hand it the whole conversation written on a scroll, plus a card of house rules (the system prompt). Where it breaks: A pen pal remembers earlier letters. The API remembers nothing, so long chats get more expensive each turn because you resend everything.

Conversations are lists you resend

The core structure — and the fact that reframes everything: multi-turn.py — the conversation IS the array messages = [ {"role": "user", "content": "I'm planning a budget trip to Goa."}, {"role": "assistant", "content": "Great! What's your budget and how many days?"}, {"role": "user", "content": "5 days, ₹15,000 total, I like beaches and food."}, ] # You resend this WHOLE list every call. Claude is stateless — # it has no memory of previous calls; the array IS the memory. copy Stateless is the key word: the API remembers NOTHING between calls (1.2's «no memory between chats», now literal). Continuity is an illusion YOU maintain by resending the growing list. The app does this for you; your product must do it itself. Consequence 1 — cost grows with the conversation (you pay to reprocess the whole history each turn — 9.6's caching is the answer). Consequence 2 — YOU control the memory: trim old turns, summarise-and-replace (2.7's restart, in code), inject relevant context — memory management is a design decision your product makes, not a feature you're given.

The system parameter and roles

system (separate from messages) — the standing instructions, casting, rules, truth-discipline (2.6, 3.4). This is where your product's SOUL lives; it's sent every call, above the conversation. The single most important string in any product you build. Roles — user and assistant alternate; the system is its own field. There's no «Claude» role invention — it's always these. Multi-turn = alternating user/assistant entries. Prefill — the dial that was retired (3.3, promised): older models let you end messages with a partial assistant turn so Claude continued FROM your words («{» to force JSON, «VERDICT:» to skip preamble). Every current model — Opus 4.6 onward, Sonnet 4.6 onward, Haiku 5.5, Fable — rejects a prefilled last assistant turn with a 400 error . The first-tokens-are-rails idea survives; the mechanism moved: ask for the opening in the system prompt («Begin every reply with 'Draft reply:'»), or use structured outputs (9.5) when you need guaranteed JSON. (Source: Opus 5.5 migration guide, platform.claude.com, checked 2026-11-03.) Mid-conversation system messages (Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.1 and others): you can append {role: 'system', content: …} inside messages to add an operator instruction later in a conversation, without editing the top-level system string and breaking the prompt cache (9.6).

The behaviour dials

Dial What it does Set it by max_tokens Hard cap on output length (required) 2.4's length control — set generously enough to finish, tight enough to bound cost output_config.effort How hard the model works: low · medium · high · xhigh · max — controls thinking depth, tool-call count and total tokens Low for chat, classification, bulk extraction; high/xhigh for coding and agent loops. Defaults differ: medium on Opus 5.5 and Haiku 5.5, high on Sonnet 5.5 and Fable 5.1 — set it explicitly thinking Adaptive thinking (2.5): the model decides how much to reason, steered by effort Leave it adaptive. The old budget_tokens form returns a 400 on every current model; Opus 5.5 and Fable 5.1 can't switch thinking off at all — lower effort instead stop_sequences Strings that halt generation when produced Cutting output at a delimiter — useful in structured pipelines stream Deliver tokens as generated (the typing effect) On for anything a human watches (felt latency); off for backend batch work Streaming deserves a word: it changes NOTHING about cost or content and EVERYTHING about felt experience — a user watching words appear at 200ms tolerates what a 9-second silent spinner makes them abandon. Perceived performance is a product feature; streaming is how you buy it nearly free. Where did temperature go? Temperature (and top_p , top_k ) reshaped the odds of the next token (Lesson 1.1's widget). Claude Opus 4.7 and every later model accept only the default, and on API version 2026-10-21 — the default in anthropic Python SDK 2.0+ and TypeScript SDK 1.0+ — sending any of the three returns a 400 on every model, even at its default value. Anthropic's own note: temperature = 0 never guaranteed identical outputs anyway. Consistency now comes from what always mattered more: a tight system prompt, examples, structured outputs (9.5), lower effort for routine work, and an eval that measures it (3.6). (Sources: platform.claude.com/docs/en/api/migration-2026-10-21 and the Opus 5.5 migration guide, checked 2026-11-03.)

The current call, end to end

Here is a streaming call with every live dial in place: stream_reply.py — the current dials, streaming (anthropic SDK 2.x) import anthropic client = anthropic.Anthropic() # reads ANTHROPIC_API_KEY SYSTEM = "You are a support-reply drafter for Ember Tea. Warm, brief, never promise refunds. Begin every reply with 'Draft reply:'." messages: list[anthropic.types.MessageParam] = [ {"role": "user", "content": "My order #4411 arrived with a cracked lid."} ] with client.messages.stream( model="claude-sonnet-5-5", max_tokens=2000, # hard ceiling on output (required) system=SYSTEM, # the product's standing rules output_config={"effort": "low"}, # low / medium / high / xhigh / max stop_sequences=["\n---"], # optional: cut at a delimiter messages=messages, ) as stream: for text in stream.text_stream: # tokens appear live print(text, end="", flush=True) final = stream.get_final_message() print("\nstop_reason:", final.stop_reason, "| tokens out:", final.usage.output_tokens) # keep the WHOLE content (thinking blocks included) for the next turn messages.append({"role": "assistant", "content": final.content}) copy Checked 2026-11-03 against anthropic 2.4.0 with a type checker (no paid call made). Notice what is not there: no temperature , no prefilled assistant turn. Both used to be core dials; on current models both are errors. The next section explains why, and what replaced them.

Recap

Conversations are stateless arrays you resend and manage; the system parameter is your product's soul; and the live dials — effort for how hard it works, adaptive thinking, streaming for felt speed, max_tokens for bounds — are your judgment made mechanical. Temperature and prefill are retired: design consistency with examples, structure and evals.

In one line: Each API call sends the whole conversation, because the API itself remembers nothing.
