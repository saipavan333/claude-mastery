9.4 · Tool Use: Giving Claude Hands

Tool use: giving Claude hands. The mechanism that lets your products query databases, call APIs, run calculations, and act in the world — the foundation of every agent.

In one breath: Tool use lets you define functions (name, description, input schema) that Claude can call — it emits a structured request, YOUR code runs the function and returns the result, and Claude continues with real data or a completed action; it's the same loop as MCP (8.1), now in your own code.

The loop you already know

You saw this exact loop in 8.1 (MCP). Now YOU own both ends: 1. You define tools — each with a name, a description (the prompt by which Claude decides when to use it — 8.1's law), and an input schema (typed parameters). You send these with your request. 2. Claude decides and requests — reading the conversation, if a tool fits, Claude returns stop_reason: 'tool_use' and a structured call: which tool, what arguments. It does NOT run anything (8.1's crucial division — the model emits; your code executes). 3. YOUR code executes — you run the actual function (query the database, call the weather API, compute), get a result. 4. You return the result — append it as a tool_result and call again; Claude continues with real data, either answering or calling another tool. tool_use.py — defining a tool tools = [{ "name": "get_order_status", "description": "Look up a customer order's current status by order ID. " "Use when the user asks about the state, shipping, or " "delivery of a specific order. Not for creating or " "cancelling orders.", "input_schema": { "type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"], }, }] # Send tools=tools with your request. When Claude returns a tool_use # block, run get_order_status(order_id) yourself and return the result. copy Recognise it? The description follows every 2.2/8.4 rule (what, when, when-NOT); the schema is 3.3's typed contract. Tool design IS the interface-craft you learned building MCP servers — same skill, your own code.

Client tools vs server tools

Client tools (you define, you run): the pattern above — YOUR functions, executed by YOUR code. This is how products connect Claude to their own databases, business logic, and external APIs. Total control, total responsibility. Server tools (Anthropic-provided, they run): built-in tools Claude can use that Anthropic executes — web search (live facts, 1.6's defense as an API feature), code execution (Claude writes and runs code in a sandbox — 4.4's analysis tool, programmable), computer use (screen control — 6.1's engine). You enable them; you don't implement them. Best of both: capability without building it. Structured mode & parallel calls: strict schemas guarantee valid tool inputs; Claude can request MULTIPLE tools in one turn (check inventory AND price simultaneously) — your code runs them and returns all results. Efficiency and power.

Tool use IS the agent foundation

An agent is a tool-use loop that keeps going (Track 10's whole subject, previewed): Claude calls a tool → sees the result → decides the next tool → repeats until the goal is met. Everything agentic — Cowork, Claude Code, Managed Agents — is this loop, elaborated. Understanding tool use is understanding agents at the mechanism level. The security weight lands here (8.5, now yours to hold): tools are the ACTION CHANNEL — the third leg of the lethal trifecta. A tool that sends email, deletes records, or spends money is exactly where injection becomes dangerous. Design tools with least privilege (read vs write vs destructive — 8.2), human hinges on consequential ones (4.7), and the trifecta audit on any agent you build (8.5). Tool DESIGN is security design. Errors that teach (8.4): a tool returning «order_id not found; did you mean one of: …» lets Claude self-correct — your tools' error messages are part of the conversation. Design them as such.

Recap

Tool use gives Claude hands: you define tools (name, steering description, typed schema), Claude requests calls, your code executes and returns — client tools for your logic, server tools for Anthropic's capabilities, and tool design IS security design because tools are the trifecta's action leg.
