8.1 · What MCP Is & Why Everyone Adopted It

The Model Context Protocol: one open standard that lets any AI plug into any tool — why it exists, how it works, and why the whole industry signed on.

In one breath: MCP is an open protocol where lightweight servers expose tools, data and prompts in a standard shape any AI client can use — solving the every-app-to-every-AI wiring problem the way USB-C solved cables, which is why Anthropic built it and rivals adopted it.

The problem and the shape of the fix

An AI model is a brain in a jar: brilliant, but it can only touch what its harness passes in. Every «Claude can read my calendar / query my database / file my tickets» requires REAL integration: auth, API calls, data formatting, error handling. Custom-built per assistant per tool, that's the M×N explosion — unmaintainable, so most useful connections simply never existed. MCP's move: standardise the middle. Tools wrap themselves ONCE as an MCP server ; AI applications implement ONE MCP client ; any client then speaks to any server. M×N collapses to M+N. That's the entire trick — and like USB-C, the boringness IS the brilliance: standards win by being unremarkable everywhere.

What a server actually offers

Three kinds of things, each with a clean job: Tools — actions the AI can take: «create_invoice», «query_orders», «send_slack_message». Each declares its name, description and typed inputs (a schema) — and the DESCRIPTION is how the model decides when to call it. (You've met this idea twice: skills' trigger-descriptions (4.8) and — spoiler for Track 9 — API tool-use. Same mechanism, three costumes: models choose tools by reading descriptions. ) Resources — data the AI can read: files, database views, documents — content addressed by URI, loaded when relevant. Prompts — reusable prompt templates the server offers («use my analyse-contract template») — your 3.5 assets, served over the wire. Under the hood: a simple message protocol (JSON-RPC) over either stdio (the server runs as a local process — how personal/local servers work) or HTTP (remote servers across the network — 8.3's territory). You'll never hand-write these messages; SDKs handle it. But knowing the two transports explains every setup screen you'll ever see.

Where you've already touched it (and why adoption snowballed)

You've been an MCP user for weeks: the app's connector directory (4.7) — largely MCP servers. Claude Code's tool ecosystem (7.5's plugins) — MCP. Cowork reaching your tools (5.2) — MCP under the hood. The protocol was the invisible floor of Phase C. Why rivals adopted a competitor's standard: ecosystems beat features. Once servers existed for thousands of tools, any AI that SPOKE the protocol inherited the whole catalogue overnight — refusing meant offering users fewer integrations out of pride. By 2026, major labs and clouds all speak it, and governance has matured into open working groups (no single-company fiat) — the standard outgrew its parent, which is exactly what good standards do. Why YOU care strategically: one skill — «I can build and secure MCP servers» — now connects you to every AI platform at once. Learn the standard, inherit the ecosystem. That's 8.4's promise, and Track 11/12 price it.

Recap

One open standard collapses M×N to M+N: servers offer tools/resources/prompts with descriptions the model chooses by; clients emit calls; servers execute; results return — you've used it for weeks, and now you can read the plumbing.
