15.1 · The Money-Agent Playbook

The Money-Agent Playbook — how to think about agents as products and services: what makes one worth paying for, the anatomy every sellable agent shares, how to pick a use case, which build stack to choose, and the five-step arc every build in this track follows.

In one breath: A money-making agent is a reliable, mostly-unattended worker that does one valuable recurring job — triaging inputs, producing reports, answering customers, processing documents — and businesses pay for the OUTCOME plus the reliability, not the AI; this lesson gives you the playbook (anatomy, use-case selection, stack choice, pricing models, and the Spec → Architect → Build → Guard → Package arc) that every build-along in this track then makes concrete.

What makes an agent worth paying for

An agent is worth money when it does a job that is valuable, recurring, and rule-followable — and does it reliably enough that a human only has to supervise, not do. Four properties separate a paid agent from a toy: It owns a recurring job, not a one-off answer. A chatbot answers a question; an agent runs a process on every new input, every day. Recurrence is where the value compounds — a job done 200 times a month is 200 times the payoff of doing it once. It produces an outcome someone already pays for. The best agents automate work a business currently does by hand or hires for: triaged leads, weekly briefings, answered tickets, extracted invoice data. If they already pay a person (or lose money not doing it), they will pay for the agent. It is reliable enough to trust with supervision. Nobody pays for an agent they must redo. Reliability comes from narrow scope, verification steps, and human-in-the-loop on anything irreversible — the engineering from 10.5, applied. It reports what it did. A paid agent leaves a trail — a log, a summary, a dashboard — so the buyer can see it working and trust it. Invisible work feels risky; visible work feels like a hire. Notice what is not on the list: being impressive, being fully autonomous, using the newest model. Buyers pay for a reliable outcome on a job they care about. That is the whole game.

The anatomy of a sellable agent (five parts)

Every agent in this track — and nearly every paid agent anywhere — is built from the same five parts. Learn them once and every build is a variation: 1. The job-to-be-done. One sentence: on each [input], produce [outcome] so that [buyer] saves [time/money]. If you cannot write that sentence, you do not have an agent yet. 2. The trigger. What starts a run — a new email, a schedule (every morning), a form submission, a file dropped in a folder. The trigger is what makes it an agent (it runs itself) rather than a prompt (you run it). 3. The loop and its tools. The agent plans, calls tools to read and act, and decides when it is done (10.1). Its tools are how it touches the world: reading a mailbox, querying a knowledge base, writing to a sheet, calling an API. Tools (9.4) and MCP (Track 8) are the hands. 4. The guardrails. Scope limits, a verification pass, and human approval on anything irreversible (sending, paying, deleting). Guardrails are not optional polish — they are what makes the agent safe to sell (10.5/10.6). 5. The delivery + report. Where the outcome lands (a draft folder, a CRM, a briefing doc) and the trail it leaves so the buyer trusts it. This is the difference between "a script ran" and "my agent handled it." Each build-along walks these five in order. When you design your own agent later, fill in the five parts first — the build follows from them.

Choosing the use case and the stack

Choosing the job. Score candidate jobs on four axes: frequency (how often it recurs), pain (how much the buyer hates or overpays for it), rule-followability (can it be done from clear instructions and available context?), and safety-to-automate (what is the worst case if it errs, and can a human gate that?). High frequency, high pain, high rule-followability, and low blast-radius is the sweet spot — that is why inbox triage and report generation are such reliable first agents. Choosing the stack. Match the build to the buyer and the job (revisit Track 10): Cowork / the app (no code) — for file-and-folder jobs and scheduled document work for one person or a small team. Fastest to ship; great for services where you run the agent for the client. Claude Code + the Agent SDK — when you need a real programmable agent loop in your own process, with tools, MCP, permissions, and sessions. The Agent SDK is "Claude Code as a library" in Python or TypeScript; it is the workhorse for custom agents you host. The API + tool use — when you want maximum control over the loop and are embedding the agent in your own product (9.4). Managed Agents — Anthropic's hosted service that runs the agent loop and sandbox for you, for long-running or asynchronous agents you do not want to operate yourself. For a first paid agent, favor the least infrastructure that delivers the outcome — often Cowork or the Agent SDK. You can always re-platform once it is earning.

Pricing models and the build arc

How agents make money (pick per job): Setup fee + monitoring retainer — the durable default: charge to build and wire it in, then a monthly fee to run, monitor, and improve it. Roughly setup $500–$5,000 and retainer $200–$2,000/mo for small-business agents; more for high-value B2B (verify current rates — see the Current facts page and Track 11). The retainer is the business, because reliability needs ongoing care. Per-outcome — price per unit of work done (per triaged lead, per briefing, per resolved ticket). Aligns your pay with value delivered; needs clean measurement. Per-seat / subscription — if the agent is a product many users run, price per user per month (12.2 unit economics apply — keep API cost well under price). Whatever the model, price on the value of the outcome (11.4), not your token cost or build time. An agent that saves a team 15 hours a week is worth far more than the API bill to run it. The build arc — every build-along follows these five steps: (1) Spec the five parts (job, trigger, loop+tools, guardrails, delivery). (2) Architect the stack and the tool list. (3) Build it step by step. (4) Guard & verify — add the safety gates and test it on real inputs until it is reliable. (5) Package & price — turn it into an offer with a demo, a report, and a price. Learn the arc here; execute it in every build that follows.

Recap

A money-making agent owns one valuable, recurring, rule-followable job and delivers a reliable OUTCOME with supervision and a visible trail — buyers pay for that, not for the AI or autonomy. Every sellable agent has five parts (job, trigger, loop + tools, guardrails, delivery + report); you choose the job by scoring frequency, pain, rule-followability, and safety, and the stack (Cowork / Agent SDK / API / Managed Agents) by matching the least infrastructure to the outcome. Price on the value of the outcome — usually a setup fee plus a monitoring retainer — and build every agent with the same arc: Spec → Architect → Build → Guard & verify → Package & price.
