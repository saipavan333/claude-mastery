3.6 · Evals: Testing Prompts Like an Engineer

«It seems better» is not a measurement. Evals turn prompt tweaking from vibes into engineering — and they're lighter-weight than you fear.

In one breath: An eval is a small fixed test set — real inputs plus what good output looks like — run against any prompt change, so improvements are measured, regressions are caught, and arguments end with data.

The minimum viable eval

Three components, one afternoon: A test set: 15–30 REAL inputs for your task — including the ugly ones (3.3's law: garbage is the job). Cover: typical cases, known-tricky cases, and at least two «should refuse / should say unknown» cases (truth behaviour is testable behaviour — 3.4). Expected outcomes: per input, what does success look like? Three grades of rigour: exact (extraction tasks: the correct JSON), criteria (open tasks: «mentions the deadline, under 100 words, no invented numbers»), reference (a gold example to compare against). A scoring pass: run the prompt on all inputs, score each pass/fail against expectations, get a number: 22/25. That number is your baseline — and the entire point: changes are judged by the number moving, not by how the latest answer felt.

Claude as the grader

Scoring 25 outputs by hand is fine once and tedious forever. The standard move: a second prompt grades the first's outputs — the LLM-as-judge pattern (your generator–critic chain from 3.1, formalised): judge template (adapt freely) You are grading outputs against criteria. For the input in <input>, the output in <output>, and the criteria in <criteria>: score each criterion PASS/FAIL with a one-line reason, then overall PASS only if all criteria pass. Be strict — when in doubt, FAIL with the doubt stated. No other text. copy Judge rules of thumb: give it CRITERIA, not taste («under 100 words» beats «concise»); keep the judge prompt frozen while you iterate the task prompt (never move both walls at once); spot-check ~5 judge verdicts by hand the first time (grade the grader before trusting it); and for high-stakes evals, a stronger model judges a cheaper model's work (1.3's mix, again).

The eval workflow that changes your behaviour

Before «improving» anything: run the baseline. You cannot improve what you haven't measured — half of clever prompt tweaks turn out to move nothing. One change, one run (2.1's discipline, now instrumented): change the role OR add an example OR tighten a rule — rerun — did the number move? Which ITEMS flipped? Item-level diffs teach more than the total: «the two refusal cases started failing» is a diagnosis; «24→22» is just weather. Regressions are the headline. The tweak that fixes case 7 and silently breaks cases 2 and 9 is how prompts rot. Evals exist to make silent breakage loud. Freeze winners into templates (3.5) WITH their eval — the template's version history becomes «v4: 24/25, up from 21». Grow the set from production: every real-world failure you meet becomes a new eval case. Your test set slowly becomes a museum of every way the task has ever gone wrong — which is exactly what makes it valuable.

Recap

Fifteen real inputs, written expectations, a frozen strict judge, one change per run, item-level diffs over totals — measured beats vibed, and every production failure becomes a test case.
