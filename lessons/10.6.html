10.6 · Agent Security: Injection, Sandboxes, Least Privilege

Agent security: where autonomy meets adversaries. The deepest application of the lethal trifecta, sandboxing, and least privilege — because an autonomous system with tools is the highest-stakes thing you can deploy.

In one breath: Securing agents is 8.5's trifecta framework at maximum stakes — an autonomous loop with tools and untrusted content is the dangerous shape by default — defended by breaking the trifecta structurally, sandboxing for blast-radius, least-privilege tools, human hinges on consequential actions, and assuming breach in the design.

Agents are the trifecta's native habitat

Recall the lethal trifecta (8.5): danger peaks when private-data access + untrusted-content exposure + an action/exfiltration channel COMBINE. Now notice: a capable autonomous agent tends to have all three by design — it accesses data (to be useful), reads content it didn't author (web, documents, user input, tool results — untrusted by default), and takes actions via tools (the whole point). Autonomy assembles the trifecta as its natural state, which is why agents are the highest-security-stakes systems you can build. The compounding danger: an agent doesn't just get injected once — it loops, so a successful injection can direct MULTIPLE actions, and the agent's own outputs (which an injection can shape) feed back into its next decisions. The attack surface isn't a single response; it's an ongoing process the attacker can try to steer. Tool results are untrusted content too (8.2): an agent that calls a compromised tool, or reads a document, or fetches a web page, is ingesting content an adversary may control — and that content enters the loop as if it were legitimate. The trifecta's «untrusted content» leg is often WIDER than builders realise. The design imperative: assume any agent that reads external content is a target, and architect so that a successful injection CAN'T cause serious harm — because prevention alone is never sufficient (8.5's structural truth).

The defense architecture (8.5's five layers, at agent stakes)

1. Break the trifecta structurally (the highest-value move): separate the legs across agents — a research sub-agent that reads untrusted web content has NO action tools and NO access to sensitive data; a separate action agent takes steps but never touches raw untrusted content (it acts on the research agent's STRUCTURED, sanitised output — the dual-model pattern from 8.5's deep-dive). Autonomy + untrusted-reading + consequential-action should rarely coexist in ONE agent. 2. Sandbox for blast-radius (assume breach): run agents in isolated environments (containers, VMs — 7.4's full-auto habitat, Managed Agents' sandbox) so a compromised agent can't reach beyond its box. Scoped file access, no ambient credentials, network egress limits. If injection succeeds, the sandbox bounds the damage. 3. Least privilege on every tool (8.2, 9.4): each tool has the minimum capability needed — read-only where possible (enforced below the AI layer, like Priya's SELECT-only DB user), no destructive tools that aren't essential (absent beats guarded — 8.4), action tools tightly scoped. The agent can only do what its tools permit, so constrain the tools. 4. Human hinges on consequential, irreversible actions (5.2, 10.5): the trifecta's action leg, gated by a person exactly where consequence and irreversibility are highest. An agent can research and draft freely; sending, paying, deleting, publishing get a human (or a hard auto-approve threshold for the trivial-and-reversible). 5. Observability and kill-switches (5.5, 10.5): log every action for audit and anomaly-detection (a breach you can SEE is a breach you can stop), and build a kill-switch (halt the agent instantly). Detection and response are defenses too — assume some attacks get through the earlier layers and make sure you'd notice and could stop them.

The agent-security mindset

Audit every agent for the trifecta BEFORE deploying (8.5's habit, now mandatory): score the three legs, and break at least one structurally wherever the stakes warrant. This audit is non-optional for any agent that reads external content or takes consequential actions. Trust boundaries are the core design artifact: map what's trusted (your code, your prompts) vs untrusted (all external content — web, docs, user input, tool results) and design so untrusted content can INFORM but never DIRECTLY CONTROL consequential actions. This mapping IS agent security architecture. The responsibility is real and yours: a deployed autonomous agent acting on your behalf (or your client's) can cause real harm — financial, reputational, data — and the accountability is the builder's. This weight is why agent security is a senior, trusted, well-paid specialty: companies need someone who provably won't ship a liability with initiative. Security enables deployment, it doesn't prevent it: the goal isn't to make agents so locked-down they're useless — it's to make them safe ENOUGH to deploy, by placing the constraints (structural separation, sandboxing, least privilege, hinges) precisely where the risk is, so the agent stays capable where it's safe and constrained where it's dangerous. Good security is what lets you deploy autonomy at all.

Recap

Agents are the trifecta's native habitat — autonomy assembles all three legs by default — so secure them by breaking the trifecta structurally (reader/actor separation), sandboxing for blast-radius, least-privilege tools, human hinges on consequential actions, and observability with a kill-switch; good security bounds a successful injection's worst case to something survivable, which is what makes deploying autonomy possible at all.
