7.5 · Skills, Sub-agents & Hooks

The crew: skills that fire mid-session, sub-agents that take the side quests, and hooks — deterministic tripwires that enforce your law whether anyone remembers or not.

In one breath: Skills bring your procedures into the terminal automatically; sub-agents run isolated side-tasks (searches, reviews, analyses) without cluttering your main session's context; hooks execute YOUR scripts at fixed lifecycle moments — guaranteed, not suggested.

School-kid picture: A workshop: recipe cards (skills) for the usual jobs, apprentices (subagents) who go do side tasks and report back, and safety switches (hooks) that stop the saw if the guard is open — no matter who is using it.

Skills in the terminal

Same skills, new hands: the 4.8 skills you built (description-triggered procedure folders) work here — but now they can act: your invoice-extraction skill doesn't just format data, it runs against the whole folder; your report skill produces the file and commits it. Project skills ship with the repo: skills can live in the project (.claude/skills/), versioned and shared — the house procedures arriving with the code, briefing any agent that works here (7.3's philosophy, extended to behaviour). Progressive loading still rules (4.8): descriptions index cheaply; bodies load when relevant. A project can carry twenty procedures and pay desk-rent only for today's. Plugins bundle it all: skills + commands + agents + MCP connections in one installable package — the ecosystem's distribution unit (you'll meet marketplaces of them; 12.4 covers selling them).

Sub-agents: side quests without side effects

What they are here: spawn a separate agent with its OWN context window for a bounded job — «search the codebase for every place dates are parsed», «review this diff for security issues», «summarise these 40 log files» — returning only the FINDINGS to your main session. The two dividends: context hygiene — the side quest's 200-file exploration doesn't flood your main desk (1.2 at architecture level; only conclusions come home); and parallelism — multiple sub-agents run simultaneously (5.6's teams, now in the terminal). Custom crew members: define named sub-agents with their own system prompts and tool permissions (.claude/agents/): a «reviewer» who only reads and critiques, a «researcher» with web access, a «tester» locked to running tests. Casting (2.6) + least privilege (5.2) = a crew you designed. When to reach for one: any task whose WORKING would clutter your session but whose ANSWER you need — searches, audits, big reads, second opinions (the fresh-context critic of 3.4, now one keystroke).

Hooks: law that fires itself

The mechanism: hooks are YOUR commands configured to run at fixed lifecycle events — before/after file edits, after bash commands, at session start/end. Configured in settings, executed deterministically: not «Claude usually remembers» but «this ALWAYS happens». The canonical uses: auto-format every edited file (the formatter runs after each edit — style debates end); run the linter/tests after changes (instant feedback into the loop); BLOCK dangerous patterns (a pre-command hook that refuses anything touching /originals — your do-not-touch list, enforced by machinery); log every action for audit (receipts, guaranteed). Why this matters beyond convenience: hooks are the difference between INSTRUCTED behaviour (CLAUDE.md asks; the model complies with high probability) and ENFORCED behaviour (the hook fires with probability 1). Your constitution's most sacred lines deserve promotion from prose to tripwire. Instructions steer; hooks GUARANTEE. Respect the power: hooks execute real commands automatically — a bad hook is an automatic bug. Test them like the machinery they are (and never install a stranger's hooks unread — 4.8's trust rule, sharpened).

Under the hood: the actual files (checked against code.claude.com, 3 Nov 2026)

Everything above is four kinds of plain file. Here is each one, small enough to copy. 1. A skill is a folder with a SKILL.md : YAML frontmatter, then instructions. It lives in .claude/skills/<name>/ (this project) or ~/.claude/skills/<name>/ (all your projects). Claude reads only the description until a request matches, then loads the body. You can also run it yourself as /branch-close . Old .claude/commands/*.md files still work, but skills are now the recommended home for custom commands. .claude/skills/branch-close/SKILL.md --- name: branch-close description: Monthly close for the branch CSV exports. Use when the user asks to process, reconcile or close a month of branch files. Not for ad-hoc questions about one file. allowed-tools: Read Grep Bash(python check.py *) --- 1. Read every file in exports/<month>/ ; never edit anything in originals/. 2. Convert amounts to paise (integers). Quarantine rows that fail check.py. 3. Write the summary to reports/<month>.md with a receipts table: files read, rows in, rows quarantined, total. copy Useful extra fields: disable-model-invocation: true (only YOU can trigger it — right for anything with side effects, like a deploy), context: fork (run it in a subagent), model / effort . The SKILL.md format itself is an open standard (agentskills.io), which Anthropic donated to the Linux Foundation's Agentic AI Foundation on 22 October 2026 — the same skill folder works in the Claude app, the API and other tools that adopt the standard. 2. A subagent is one Markdown file in .claude/agents/ : frontmatter with name and description (required), optional tools allowlist and model ; the body becomes its system prompt. Ask «use the reviewer subagent on my changes», or @-mention it. .claude/agents/reviewer.md --- name: reviewer description: Reviews a diff for bugs and risky changes. Use after edits to scripts, before committing. tools: Read, Grep, Glob model: sonnet --- You review code. Read only; never edit. Report findings as file:line - problem - suggested fix, most severe first. If you find nothing, say so plainly. copy 3. Hooks live under a hooks key in .claude/settings.json (committed, whole team), .claude/settings.local.json (just you) or ~/.claude/settings.json (every project). Each entry names a lifecycle event — PreToolUse , PostToolUse , UserPromptSubmit , SessionStart , Stop and about thirty more — a matcher for the tool name, and a command to run. .claude/settings.json — two tripwires { "hooks": { "PreToolUse": [ { "matcher": "Write|Edit|Bash", "hooks": [ { "type": "command", "command": "python \"${CLAUDE_PROJECT_DIR}/.claude/hooks/protect_originals.py\"" } ] } ], "PostToolUse": [ { "matcher": "Write|Edit", "hooks": [ { "type": "command", "command": "python check.py --quick" } ] } ] } } copy Claude Code pipes the pending tool call to your command as JSON on stdin ( tool_name , tool_input , cwd and more). The contract is the exit code: 0 = allow , 2 = block (on PreToolUse the call is cancelled and your stderr text is shown to Claude as the reason), anything else = a non-blocking error. Here is the guard script: .claude/hooks/protect_originals.py import json, sys # Claude Code sends the pending tool call as JSON on stdin call = json.load(sys.stdin) tool = call.get("tool_name", "") args = call.get("tool_input", {}) target = args.get("file_path", "") + " " + args.get("command", "") if "originals/" in target.replace("\\", "/"): print("Blocked: nothing may write to originals/. Work on a copy in work/.", file=sys.stderr) sys.exit(2) # exit 2 = block the call; stderr is shown to Claude as the reason sys.exit(0) # exit 0 = allow copy Tested 2026-11-03 by piping sample PreToolUse JSON into it: a Write to originals/ and an rm -rf originals/2026 both exited 2 with the message; an Edit in work/ exited 0. It is a teaching guard, not a sandbox: a determined command can dodge a string match (a variable holding the path, say). Real protection layers it with file permissions and Claude Code's own permission rules. 4. A plugin bundles skills, agents, hooks and MCP servers into one folder you can install, version and share. (A plugin whose hooks are written as a JavaScript module is called a mod .) plugin layout + install rekha-close/ # one folder = one installable unit .claude-plugin/plugin.json # {"name": "rekha-close", "version": "1.0.0", "description": "..."} skills/branch-close/SKILL.md # runs as /rekha-close:branch-close agents/reviewer.md # a subagent Claude can delegate to hooks/hooks.json # same "hooks" shape as settings.json .mcp.json # optional: MCP servers the plugin starts # try it locally without a marketplace claude --plugin-dir ./rekha-close # share it: list it in a marketplace repo (.claude-plugin/marketplace.json), then teammates run /plugin marketplace add your-org/your-marketplace /plugin install rekha-close@your-marketplace copy Two cautions from the docs worth remembering: every enabled plugin puts its skill and agent descriptions into context on every turn, so unused plugins cost tokens; and whatever a plugin runs, it runs as you — read it before you install it. (Sources: code.claude.com/docs/en/skills, /sub-agents, /hooks, /plugins.)

Recap

Skills carry procedure into the terminal, sub-agents take bounded side quests and return only findings, hooks turn sacred rules into machinery — instructed steers, enforced guarantees, and your workshop now has both.
