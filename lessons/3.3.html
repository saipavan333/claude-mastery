3.3 · Prefilling & Structured Extraction

Prefilling, extraction contracts, and answer-shaping: how to make Claude's output start exactly where you want and land exactly where your tools need.

In one breath: You can shape the very first token of Claude's answer — by instruction in chat («begin directly with…») or literal prefill on the API — and combine it with strict extraction contracts to get machine-grade output from a language model.

First tokens rule everything after them

Generation is autoregressive: each token conditions on everything before it (1.1, 2.5). So the opening of the answer isn't decoration — it's the rails. If the answer begins «Great question! There are several ways to think about this…», you've bought a hedge-and-ramble trajectory. If it begins with a table header, you get a table. Steering moves, in rising strength: Ban the preamble (2.4): «No preamble. Begin directly with the verdict.» Dictate the opening: «Begin your response with exactly: VERDICT: » — the model must continue from a committed frame. Literal prefill (API — Lesson 9.2): on the API you can write the beginning of the assistant's turn yourself — start it with «{» and JSON becomes overwhelmingly likely; start with «VERDICT:» and no pleasantries can exist. Chat gives you ~90% of this via instruction; the API makes it mechanical.

Extraction contracts: the strict version of format specs

When output feeds a spreadsheet, script, or downstream prompt (3.1 chains!), «mostly right format» = broken. An extraction contract is a format spec with the screws tightened: Exact schema by example (2.3+2.4): show the precise keys/columns, with one filled example row. Type discipline: «dates as YYYY-MM-DD; amounts as numbers without currency symbols; missing → null (never guess, never omit the key).» Totality rule: «one output row per input item, even for rejects (mark status: SKIPPED + reason)» — silent drops are the deadliest extraction bug. No-other-text rule: the output IS the artifact — no explanation before, no summary after. Self-check clause: «before finishing, verify: row count equals input count; all dates parse; then output only the data.» Cheap, surprisingly effective. On the API, structured outputs make schema-compliance a guarantee (9.5) — but the CONTRACT thinking (types, totality, null-honesty) stays yours; a guaranteed-valid schema can still contain guessed values if you never wrote the never-guess clause.

Answer-shaping patterns worth stealing

The committed-verdict pattern: «First line: APPROVE / REJECT / NEEDS-INFO. Then justification.» Forces the decision before the rationale — no more essays that never conclude. (For hard reasoning, combine with 2.5: think in <thinking>, THEN commit.) The differential pattern: «Output only what CHANGED from the previous version, as a list of edits.» Perfect for revision loops (2.7) — and it's how you review a 30-page revision in one minute. The traffic-light pattern: force every item into green/yellow/red with one-line reasons — decisions love discrete states (you saw it in 1.6's triage; now you're the one imposing it). The fill-the-blanks pattern: paste a template with ____ slots and «fill only the blanks; change nothing else». The strongest format control available in pure chat — the document IS the contract.

Recap

First tokens are rails — commit them; extraction is a contract — schema by example, types, totality, null-honesty, no-other-text, self-check; and test contracts on garbage, because garbage is the job.
