14.3 · Capstone C: MCP Server + Code Workflow

Capstone C — build a real MCP server, wire it into Claude Code, and run a genuine developer workflow with it: giving Claude a custom tool and using it in a build, done securely.

In one breath: This third capstone crosses into the builder's world: you'll build a working MCP server (from 8.4) that exposes a genuinely useful tool or data source, wire it into Claude Code or the desktop app, and use it inside a real developer-style workflow (7.8) — done with the security discipline (8.5) that separates a safe integration from a dangerous one, and packaged as a portfolio artifact that proves you can extend Claude's capabilities and drive an agentic build.

The build brief (a useful server, wired and used)

Your brief has three parts — build, wire, use: Build a useful MCP server (8.4): pick a capability Claude doesn't have built in that would genuinely help you — read/query a specific data source (a local database, a file store, an API you use), perform a specific action (create records, run a calculation, fetch domain data), or integrate a service. Build it as an MCP server exposing clear, well-described tools. "Useful to you" is the bar — this should be something you'd actually want Claude to be able to do. Wire it into Claude Code or the desktop app (8.2): configure the server so Claude can discover and call its tools, with the permission and safety settings done correctly. The wiring is where MCP's plug-in promise becomes real — your custom capability now available to Claude. Use it in a real workflow (7.8): drive a genuine task that uses your server's tools inside the pro loop — plan the work, let Claude use your tool to do it, verify the result, and commit/document. The workflow demonstrates the server in action, doing real work. Do it securely (8.5): apply the security discipline — least privilege (the server can only do what it needs), awareness of the lethal trifecta (private data + untrusted content + exfiltration channel), and safe permission settings. A wired tool with the wrong permissions is a liability; security is part of the build, not an afterthought. Deliverable: the working server (code + clear tool descriptions), evidence of it wired and used in a workflow (a demo, a transcript, a short write-up), and notes on the security choices you made.

The architecture (server, transport, client, workflow)

The MCP integration has four parts, each from Track 8: The server (8.4): your code that exposes tools — each tool a clearly-named, well-described function with typed inputs/outputs. The tool descriptions matter enormously: Claude decides when and how to call your tools based on their descriptions, so clear, accurate descriptions are what make the server usable (bad descriptions = Claude misuses or ignores your tools). The transport (8.1/8.3): how the client reaches the server — local (stdio, for a server on your machine) or remote (for a hosted server). For a personal capstone, local is simplest; remote (8.3) is the path if you later want others to use it. The client (8.2): Claude Code or the desktop app, configured to connect to your server, discover its tools, and call them with your permission settings. This is where you control what the server is allowed to do. The workflow (7.8): the actual task that exercises the server — Claude, driven by you, plans a job, uses your tool(s) to accomplish part of it, and you verify. This closes the loop from 'I built a tool' to 'Claude used my tool to do real work,' which is the whole point. The elegance of MCP (8.1): build the server once, and it works with any MCP client — your capstone server could plug into Claude Code, the desktop app, or others, unchanged. You're building a reusable capability, not a one-off integration.

Doing it right (descriptions, security, verification)

Tool descriptions are the interface (8.4): invest in clear, accurate descriptions of what each tool does, when to use it, and what its parameters mean — because Claude's ability to use your server well depends entirely on them. A great tool with a vague description is unusable; a simple tool with a precise description is a joy. Treat descriptions as the most important part of the server. Least privilege always (8.5/10.6): the server should have the minimum access it needs and no more (read-only if it only reads; scoped to specific data, not everything). If the server is compromised or misused, least privilege limits the damage. This is non-negotiable for anything touching real data or actions. Mind the lethal trifecta (8.5): if your server exposes private data AND the workflow ingests untrusted content AND there's a way to send data out, you have injection-exfiltration risk — break the chain (isolate untrusted content, gate outbound actions, don't combine all three carelessly). Know this cold; it's the defining MCP security lesson. Verify the workflow's output (1.6/10.5): when Claude uses your tool to do work, verify the result — tools can be called with wrong arguments, return unexpected data, or be used in unintended ways. The verification step from the pro loop (7.8) applies fully here. Let Claude Code help you build it (7.1/7.5): you don't have to write the server alone — Claude Code can help you build the MCP server itself (it knows the MCP SDK), which is a lovely demonstration of the tools building the tools. Non-coders: this is your path in.

Recap

Capstone C builds a real MCP server exposing a genuinely useful, precisely-described tool (scoped to least privilege), wires it into Claude Code or the desktop app with correct permissions, and uses it in a real workflow via the pro loop — with the lethal-trifecta risk reasoned through and the output verified; built collaboratively with Claude Code (non-coders included), it proves the rare, premium builder skill of EXTENDING Claude's capabilities with custom tools and driving an agentic workflow, done securely.
