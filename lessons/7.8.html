7.8 · The Pro Loop: Plan → Build → Verify → Commit

The pro loop: plan → build → verify → commit — the complete working rhythm, the git literacy that anchors it, and the shipping discipline that turns sessions into a portfolio.

In one breath: Professional Claude Code work runs one loop: plan (architect before acting), build (small steps, reviewed diffs), verify (tests and receipts as law, not vibes), commit (small, described, shippable) — with git as memory and the repo as your growing proof-of-work.

The four beats, assembled

PLAN — before non-trivial work: plan mode or «plan first» (7.4), the terrain audit for new territory (7.7), and the partition for parallel work (7.6). The beat's law: disagreement is cheapest here (5.2, eternal). Skip only what's genuinely trivial — and notice how rarely that's true. BUILD — small steps (7.2), diffs actually read (scope/intent/surprises), corrections by keep/change/because (2.7), skills carrying procedure (7.5), sub-agents taking side quests. The beat's law: reviewability decays with step size — bites, always. VERIFY — the receipts YOU specified (5.1): tests pass, counts reconcile, spot-checks sample, /receipts runs (7.4), hooks enforce the sacred (7.5). The beat's law: verification is specified before building, not improvised after — you learned this as 3.6's eval-first discipline; here it's tests-and-receipts-first. COMMIT — small, with a message that says WHY («fix duplicate-count on merge overlap» not «changes»), leaving the project always-shippable. The beat's law: durable progress is chosen, not accumulated.

Git in twenty honest minutes

You've used git as «the save-point system» since 7.2. The five-verb literacy that completes it (commission Claude Code to demonstrate each — it's the best git tutor alive): commit — a named save-point of everything (you know this one — it's beat four). branch — a parallel timeline: «try the risky redesign on a branch» = experiments that can't hurt main (worktrees, 7.6, are branches with their own folders). merge — timelines rejoining (with your seam-checks, 5.6/7.6). log / diff — the memory: what changed, when, why — your receipts' receipt. push — publishing to a remote (GitHub and kin): backup + sharing + the portfolio move (below). And the security law that rides with push: secrets never enter the repo — keys and passwords live in environment files that git is told to ignore (.gitignore); one leaked-key incident teaches this at ruinous prices, so learn it at zero (ask Claude Code: «set up proper secret handling for this project» — it's a five-minute install of a lifetime habit).

Shipping: the loop's compounding exit

Every project ends shippable: a README (what this is, how to run it — commission it: «write the README a stranger needs»), the run-notes (7.7), receipts current, secrets clean. «Done» means «someone else could pick this up» — including future-you, the most frequent stranger. Push the portfolio-worthy: a public GitHub of your real automations — the branch-file pipeline, the archive-indexer, the estate scripts — is 2026's most credible resume artifact: verifiable, runnable, undeniable (13.3 builds on exactly this; start feeding it now). The loop closes into the staircase: shipped project → its procedures become skills → its runs become schedules → its patterns become templates for the next project — everything you build makes the next build faster. That compounding, sustained for months, is what «10× operator» actually means from the inside: not speed — accumulated, reusable, verified LEVERAGE.

Recap

Plan with receipts pre-specified, build in reviewed bites on branches, verify against the plan (failures become tests), commit whys and ship stranger-ready — five git verbs anchor it, secrets never enter repos, and the loop's output is a portfolio that argues for you.
